# Writing a one-shot builder brief

The brief is where the one-shot is won. The builder will do what it can verify, and it can only verify what is local, static and isolated. Fill `templates/builder-brief.md` in this order.

## 1. Restate the idea in the user's words
Quote the user's own nouns: the features, the vibe, the "later" items. Keep the full vision in the brief so the PLAN can record it. Don't paraphrase it away.

## 2. Name the first slice and the signature interaction
- If the user said "start with X", X is the slice.
- Otherwise, pick the smallest slice that shows the most distinctive thing (for example, "3D flip cards").
- Spell out the slice as numbered user-visible features, at most 5 or 6.

## 3. Write the OUT list
List every "later" item, plus accounts, payments, server storage, AI-written content, community, native apps, translations and third-party geocoding or APIs. Say "out on purpose; leave room in the data model".

## 4. Isolation and repo facts
- Give the repo, the folder to create, and the existing apps and deploy configs that must stay byte-identical.
- Name the base branch.
- Don't guess domains or hosting. Say "no deploy".

## 5. Stack guidance (suggest it, don't over-prescribe)
"Static output, TypeScript, minimal framework, one specialist library for the signature feature, confined to one module; bake data at build time; local storage with export and import." Let the builder pick versions.

## 6. Design
- Ask for a **named art direction** with palette hex values, type, ornament and motion rules.
- Reuse brand fonts and colours from the repo if any exist.
- Ask for full-page mockups, desktop and mobile, committed before app code.
- Content must be original or public-domain, and generated by code where possible.

## 7. Deliverables
- Docs: PLAN.md, RESEARCH.md, a URL sheet, mockups, and process screenshots per milestone with CAPTIONS.md.
- The app in its folder, with a README covering run, test and layout.
- Unit tests, e2e smoke tests (desktop and mobile), and a screenshot script with seeded sample data.

## 8. Verification
Paste the checklist from `templates/verification-checklist.md`. Require software-GL flags if WebGL is involved.

## 9. Guardrails
- Open a PR only: no merge, no deploy, no secrets.
- No runtime third-party calls.
- No copyrighted assets.
- Add any domain disclaimers (health, finance, legal).
- Keep the user's tone rules.

## 10. Report format
The PR body has these sections: What this is, What's in it, How to run, Test counts, Rules followed, Known weak spots.

## Checks before launch
- Is the brief tight, about 300–700 words? The exact length of the original Aftercare brief isn't on record.
- Does anything in the slice need a login, a server or secrets? If so, cut it or stub it.
- Is another open PR touching the same files? If so, wait, or isolate.
- Is exactly one agent being launched for this task?
